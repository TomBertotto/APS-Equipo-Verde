# Plan de implementación - US6: Gestión del calendario de carreras

La US6 pide que el **Administrador FIA** pueda **cargar, modificar y eliminar** fechas de carreras y eventos deportivos del calendario oficial, de modo que la información esté centralizada y actualizada, y que los cambios se reflejen al consultar (escuderías/público). El alcance es **solo gestión (CRUD)**. La consulta/descarga para escuderías/público corresponde a **US7** (Sprint 1).

Dado que el proyecto sigue un patrón muy claro (teams/drivers: tabla + router + servicio + viewmodel + UI), replicaremos ese mismo patrón para mantener coherencia.

## 1) Alcance y criterios de aceptación

**Criterios (Sprint 0):**
1. El administrador de la FIA puede cargar, modificar y eliminar una fecha del calendario.
2. El calendario consultado por escuderías y público refleja los cambios realizados por el administrador FIA.
3. La gestión del calendario está disponible tanto en la aplicación web como en la móvil.

**Actor:** Administrador FIA. Requiere autenticación + permiso adecuado (RBAC).

## 2) Modelo de datos (Backend)

Crear tabla `events` (o `races`). Se elige `events` porque abarca "carreras y eventos deportivos". Usar **soft delete** para coherencia con `teams` y `drivers`.

**Propuesta de esquema (Postgres):**
```sql
CREATE TABLE IF NOT EXISTS events (
  id SERIAL PRIMARY KEY,
  name TEXT NOT NULL,
  circuit TEXT NOT NULL DEFAULT '',
  location TEXT NOT NULL DEFAULT '',
  category TEXT NOT NULL DEFAULT 'F1',
  event_date DATE NOT NULL,
  event_time TIME,
  status TEXT NOT NULL DEFAULT 'scheduled',
  notes TEXT NOT NULL DEFAULT '',
  deleted_at TIMESTAMP
);
```

**Justificación de campos:**
- `name`: Nombre del evento (ej. "Gran Premio de España")
- `circuit`: Circuito (coherente con US que habla de carreras/eventos)
- `location`: Ciudad/país (útil para visualización)
- `category`: Categoría (F1/F2/F3/F1 Academy) para mantener coherencia con `teams.category`
- `event_date` + `event_time`: Fechas/horarios. US6 habla de "fechas de carreras y eventos deportivos" (basta con fecha; hora opcional para futuro)
- `status`: Estado (valores sugeridos: `scheduled`, `completed`, `cancelled`, `postponed`). No lo exige US6 pero útil y no añade complejidad; por defecto `scheduled`
- `notes`: Observaciones
- `deleted_at`: Soft delete (coherente con patrón existente)

**Validaciones a nivel backend:**
- `name` obligatorio
- `event_date` obligatorio (formato válido)
- `category` opcional (default F1)
- `status` debe pertenecer a valores permitidos si se valida (evitar datos inválidos)

## 3) Permisos (RBAC)

Actualmente `PERMISSIONS = ['profiles.manage', 'users.manage']` y `admin` los tiene todos.

US6 es gestión administrativa exclusiva de **Administrador FIA**. Lo más coherente con el modelo actual es **crear un nuevo permiso** `calendar.manage` (naming claro, reutilizable para US7 si hiciera falta separar).

**Cambios necesarios:**
- `backend/src/permissions.ts`: agregar `calendar.manage` a `PERMISSIONS` (array). El rol `admin` ya recibe todos los permisos (`role === 'admin' return PERMISSIONS`), por lo que no requiere seed adicional.
- `backend/src/db.ts`: no requiere cambio (permisos se calculan dinámicamente o via `role_permissions`; admin bypass).

**Decisión:** Añadir `calendar.manage`. Esto no rompe roles existentes y deja preparado US7 (consulta pública no requiere permiso; gestión sí).

## 4) Backend - API / Rutas

Crear nuevo router `eventsRouter` en `backend/src/calendar.ts` (o `events.ts`). Replicar patrón de `profiles.ts` (CRUD + soft delete + validaciones + protecciones).

**Endpoints propuestos:**

| Método | Ruta | Auth | Permiso | Descripción | Criterio |
|---|---|---|---|---|---|
| `GET` | `/events` | Público | — | Listar eventos **no eliminados** (ordenados por fecha ascendente). **Necesario** para que "el calendario consultado..." refleje cambios (Criterio 2). | CA2 |
| `GET` | `/events/:id` | Público | — | Obtener evento por ID (útil para edición futura) | Soporte |
| `POST` | `/events` | Sí | `calendar.manage` | Crear evento | CA1 |
| `PUT` | `/events/:id` | Sí | `calendar.manage` | Modificar evento | CA1 |
| `DELETE` | `/events/:id` | Sí | `calendar.manage` | Eliminar (soft delete `deleted_at = NOW()`) | CA1 |

**Notas:**
- `GET /events` público: cumple CA2 (escuderías y público consultan y ven cambios inmediatos). Esto prepara US7 sin duplicar lógica.
- Usar soft delete en listados (`WHERE deleted_at IS NULL`).
- Orden sugerido: `ORDER BY event_date ASC, event_time ASC NULLS LAST, id ASC`.
- Respuestas: devolver objeto creado/actualizado en POST/PUT (coherente con teams).

**Registro de rutas:** En `backend/src/index.ts` añadir `import { eventsRouter } from './calendar.js'` (o nombre elegido) y `app.use('/events', eventsRouter)`.

## 5) Frontend - Modelo/Servicios

Crear `app/src/models/CalendarService.ts` siguiendo `ProfilesService.ts`.

**Types:**
```ts
export const EVENT_CATEGORIES = ['F1', 'F2', 'F3', 'F1 Academy'];
export const EVENT_STATUSES = ['scheduled', 'completed', 'cancelled', 'postponed'];

export type Event = {
  id: number;
  name: string;
  circuit: string;
  location: string;
  category: string;
  event_date: string; // ISO date YYYY-MM-DD
  event_time: string | null; // HH:MM:SS o HH:MM
  status: string;
  notes: string;
};

export type EventInput = Omit<Event, 'id'>;
```

**Métodos:**
- `getEvents()` → `GET /events`
- `createEvent(event: EventInput)`
- `updateEvent(id: number, event: EventInput)`
- `deleteEvent(id: number)`

**DI:** Registrar `CalendarService` en `app/src/di/container.tsx` (crear instancia y añadir a `Container` type). Coherente con servicios existentes.

## 10) Validaciones y reglas de negocio

- **Crear/Editar:** `name` requerido. `event_date` requerido (no vacío, formato YYYY-MM-DD válido). Si inválido → 400.
- **Eliminar:** Soft delete (no borra físico). Cambios inmediatos en GET `/events`.
- **Orden:** Listado por `event_date ASC, event_time ASC NULLS LAST` para calendario cronológico.
- **Estados:** Restringir a `EVENT_STATUSES` permitidos (validación backend). Default `scheduled`.
- **Categorías:** Valores permitidos o libre? Coherente con `teams` (tiene categorías fijas) → sugerido validar contra `EVENT_CATEGORIES`.
- **Fechas pasadas:** US6 no lo prohíbe (permite cargar histórico). No agregar restricción salvo formato válido.

(Las recomendaciones son buenas, seguirlas)

2. **Formato hora:** ¿se requiere hora? Si sí, ¿formato HH:MM o incluir segundos? Propuesta `HH:MM` (más simple UI).

5. **UI fechas:** ¿preferís DatePicker nativo (expo) o input texto `YYYY-MM-DD`? Input texto mantiene simpleza (sin nueva dependencia). Ambos válidos; texto más consistente con estado actual.
